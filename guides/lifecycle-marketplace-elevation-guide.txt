1. WHAT THIS MARKETPLACE IS AND WHAT STORY IT TELLS
================================================================================

PURPOSE
-------
The Lifecycle Marketplace is the governed delivery layer of the DEWA Digital
Transformation Management Platform (DTMP). It wraps strategic intent — surfaced
from the Portfolio Management marketplace — into formal, auditable, multi-stage
initiatives. It is the operational home of the TO (Transformation Office).

The marketplace serves three distinct user populations simultaneously:
  - Division staff / initiative owners: who execute delivery
  - Senior stakeholders / division heads: who monitor and approve
  - TO office staff: who govern, support, and ensure compliance across all

NARRATIVE SPINE
---------------
The story this marketplace must tell, in order:

  Portfolio identifies a gap or opportunity (app flagged for retire/modernise,
  architecture gap, new capability needed)
          ↓
  Lifecycle wraps it in a formal governed initiative (type selected, template
  assigned, approval sought)
          ↓
  Delivery happens through one or more projects under that initiative, with
  gate approvals, risk management, blocker escalation, and service requests
  to the TO for support
          ↓
  The TO governs the full portfolio of initiatives across divisions, surfaces
  systemic risks, approves gates, and delivers support outputs
          ↓
  Benefits are tracked post-initiative to prove the value of governed delivery

POSITIONING STATEMENT (for UI copy and orientation)
----------------------------------------------------
"Lifecycle Management is where DEWA's strategic intentions become governed
reality. Every initiative — from app retirement to AI deployment — moves
through a defined stage-gate process with full accountability, TO support,
and measurable outcomes."

WHAT MAKES IT DISTINCT FROM A PROJECT TRACKER
----------------------------------------------
This is not Jira. It is not a task list. The differentiators are:
  - Formal initiative frameworks specific to DEWA's transformation types
  - Stage-gate governance with multi-level approvals
  - TO office as an active support function (19 service types, SLA-governed)
  - Cross-initiative portfolio visibility for the TO office
  - EA alignment scoring connecting delivery to architecture strategy
  - Benefits realization tracking post-closure

Every design decision should reinforce governance, accountability, and
strategic alignment — not just task management.

3. STAGE 2 & STAGE 3 UNIFICATION — THE PROBLEM AND FIX
================================================================================

CURRENT STATE
-------------
Stage 2: UNIFIED. All marketplaces route to Stage2AppPage.tsx which detects
the active marketplace from the route path and renders the appropriate workspace.
Lifecycle Management correctly participates in this unified Stage 2. No change
needed here.

Stage 3: PARTIALLY UNIFIED. Most marketplaces route to Stage3AppPage.tsx.
But Lifecycle Management (LCStage3Page.tsx) and Portfolio Management
(PMStage3Page.tsx) have their own standalone Stage 3 pages — they are NOT
routed through Stage3AppPage.tsx.

WHY THIS MATTERS
----------------
The TO office is the single user of Stage 3 across ALL marketplaces. When a
TO officer moves between governing lifecycle initiatives, portfolio health,
solution specs, and document studio — they should feel like they are in one
unified governance workspace, not jumping between separate products with
different chrome, navigation patterns, and layout conventions.

WHAT TO DO
----------
Option A (Minimal): Keep LCStage3Page.tsx and PMStage3Page.tsx as standalone,
but ensure they share the exact same outer shell (header, nav tabs, layout
wrapper) as Stage3AppPage.tsx. The TO user sees consistent chrome even if the
content components differ.

Option B (Full unification): Refactor Stage3AppPage.tsx to accept a new scope
value "lifecycle-management" and "portfolio-management", and route both through
the unified page. LCStage3Page content becomes a scoped sub-component inside
Stage3AppPage.

RECOMMENDATION: Option A is lower risk and sufficient for the prototype.
Option B is the correct long-term architecture. Implement Option A now, plan
for Option B in a subsequent sprint.

OPTION A IMPLEMENTATION STEPS:
1. Identify the outer shell wrapper used in Stage3AppPage.tsx (the layout
   component, header, scope navigation tabs, TO user context bar).
2. Extract that shell into a shared component:
   src/components/stage3/Stage3Shell.tsx
3. Wrap LCStage3Page.tsx and PMStage3Page.tsx in Stage3Shell.
4. Ensure the scope navigation tabs in Stage3Shell include "Lifecycle Management"
   and "Portfolio Management" as clickable scopes that navigate to their
   respective routes.
5. TO user should be able to switch between lifecycle, portfolio, solution-specs,
   document-studio scope without losing the TO navigation context.

14. RAG AUTO-SCORING
================================================================================

PROBLEM:
  RAG (Red/Amber/Green) health status is manually set on initiatives.
  Manual RAG in a governance tool is an anti-pattern — it is subjective
  and can be gamed. The TO office needs a computed RAG baseline.

SOLUTION:
  Add a computeInitiativeRAG() function to lifecyclePortfolioStore.ts:

  function computeInitiativeRAG(initiative: Initiative): RAGStatus {
    const risks = getRisksByInitiativeId(initiative.id)
    const blockers = getBlockersByInitiativeId(initiative.id)
    const overdueDays = calculateOverdueDays(initiative.targetDate)
    const budgetOverrunPct = initiative.budget
      ? ((initiative.budgetSpent - initiative.budget) / initiative.budget) * 100
      : 0

    const criticalRisks = risks.filter(r => r.severity === 'Critical' && r.status === 'Open').length
    const unresolvedBlockers = blockers.filter(b => !b.resolved).length
    const escalatedBlockers = blockers.filter(
      b => !b.resolved && b.escalationStatus !== 'Not Escalated'
    ).length

    // RED conditions (any one triggers Red):
    if (criticalRisks >= 2) return 'Red'
    if (budgetOverrunPct > 15) return 'Red'
    if (overdueDays > 30) return 'Red'
    if (escalatedBlockers >= 2) return 'Red'

    // AMBER conditions (any one triggers Amber):
    if (criticalRisks === 1) return 'Amber'
    if (budgetOverrunPct > 5 && budgetOverrunPct <= 15) return 'Amber'
    if (overdueDays > 0 && overdueDays <= 30) return 'Amber'
    if (unresolvedBlockers >= 3) return 'Amber'

    return 'Green'
  }

USAGE:
  In all initiative card renders and cockpit views, replace the raw
  initiative.rag display with computeInitiativeRAG(initiative).
  Keep initiative.rag as a manual override field — if rag is explicitly
  set by the initiative owner, show that instead BUT display a small
  "Manual override" indicator next to the badge.
  This preserves human judgment while establishing a computed baseline.

  Show a tooltip on the RAG badge explaining why it is Red/Amber:
  "2 open Critical risks detected" or "Budget 18% over forecast"
